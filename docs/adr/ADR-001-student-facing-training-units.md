# ADR-001：前台按训练任务/方法组织，微能力留在后台诊断

- **状态**：Accepted
- **日期**：2026-09-08
- **范围**：速算训练前台信息架构、专项训练产品边界、能力树与学生训练项目的关系
- **关联方案**：[TRAINING_PRODUCT_ARCHITECTURE_PLAN.md](../../TRAINING_PRODUCT_ARCHITECTURE_PLAN.md)

## 背景

阶段4完成后，程序已经建立纯计算层 160 个正式叶子能力，并逐步做到：

`skill_id → 分步记录 → Mastery → Diagnostic → 推荐`

为了保证每个叶子能力都可验证、可单独生成，开发阶段曾把 160 个能力都接成 `skill_drill`。随后为了降低手机端选择成本，又把它们先按若干大类分组，再允许用户进入具体能力。

首轮手机真实验收暴露出一个产品层问题：

> **后台为了诊断而拆得越细，不代表前台就应该让学生按同样颗粒度选择训练。**

用户从备考者视角提出：资料分析速算真正需要主动练的计算种类并不多；“试商过高回退、求余、误差传播、运算顺序、基准选择、连续进位”等应该由程序在后台分析出来，而不是每个都设计成学生主动进入的专项。

进一步讨论后又明确：

- 乘法口诀一类要求极快反应，应优先做成选择/点选；
- 普通计算应让用户直接填写结果；
- 包子法、放缩法、后续假设分配等完整方法，应让用户在**一个界面**中填写多个关键中间量，而不是把每一步拆成独立训练入口；
- 用户已有的“放缩法 + 一阶/二阶 + 选项判断”界面属于后续第三层资料分析实战决策的参考，不应因为当前界面设计讨论而提前混入第一层。

因此需要重新确定“能力树”和“前台训练项目”的职责边界。

---

## 决策过程

### 方案 A：160 个叶子能力全部作为学生专项

**曾采用。**

优点：

- 每个节点都能直接测试；
- 开发和诊断映射最直接；
- 便于验证生成器是否完整。

问题：

- 学生必须理解内部能力分类；
- 训练前选择成本极高；
- 手机端页面过长；
- 把“程序如何诊断”错误地变成了“学生应该如何学习”。

**结论：否决作为正式学生 UI；可保留为开发/调试能力。**

### 方案 B：先按 9 个左右大类分组，再展开叶子能力

**首轮手机信息架构收口采用。**

例如基础口算、百分比/分数、数位/基准、顺序/拆分/近似、r与修正量、直除、包子法、补偿放缩、误差/比较。

优点：

- 比直接铺 160 个能力更容易浏览；
- 仍保持全部叶子可达。

手机真实使用后仍发现：

- 用户依然需要理解“数位/基准、运算顺序、近似取舍”等后台概念；
- 同一个方法被继续拆成过多子项；
- 仍然是“能力树导航”，只是多了一层目录。

**结论：作为过渡版本可以使用，但不作为最终学生产品结构。**

### 方案 C：前台按学生实际训练任务/完整方法组织，后台保留微能力诊断

前台只让学生选择少量真正有意义的训练项目，例如：

- 乘法口诀；
- 分数百分数；
- 加减法；
- 乘法；
- 普通除法；
- 直除完整流程；
- 包子法；
- 补偿放缩；
- 数值比较；
- 系统生成的弱项强化。

一个前台项目可以同时覆盖多个 `skillId / stepSkillId / structureTags`。

学生做题后，程序继续在后台判断：

- 哪种结构慢；
- 哪一步容易错；
- 是否属于“正确性优先”或“会但慢”；
- 下一轮应该增加哪些结构。

**结论：接受。**

---

## 最终决策

### 决策 1：能力树属于后台，不属于学生菜单

160 个正式叶子能力继续保留，并继续作为：

- 生成器结构控制；
- 每题/每步标签；
- Mastery 聚合单位；
- Diagnostic 下钻目标；
- 自动弱项强化依据。

但正常学生 UI 不再提供“浏览全部叶子并逐个训练”的主要路径。

### 决策 2：学生可见专项按“任务 / 方法”组织

新的学生前台专项必须满足：

> 学生能直接说出“我今天想练这个”。

例如“乘法”“普通除法”“包子法”，而不是“连续进位”“试商过高回退”“二阶必要性判断”。

### 决策 3：交互形式由训练目标决定

- **反应型**：选择题 / 快速点选；
- **结果型计算**：数字填入；
- **完整方法型**：单界面结构化多输入。

不再为了组件复用而强迫所有训练使用同一种输入方式。

### 决策 4：完整方法不拆成前台微专项

例如“补偿放缩”可以在一个界面中同时包含：

`基准 → r → Q0 / 粗算 → 一阶修正 → 一阶结果 → 必要时二阶`

后台仍分别计时、判定和记录对应的能力节点。

同理，包子法可以在一个完整训练界面中包含主块、余量、下一块、尾量、累计百分比和停止判断，而不要求学生逐个选择这些步骤训练。

### 决策 5：弱项训练由系统生成

程序根据历史数据输出最多 1～2 个自然语言瓶颈，并提供“开始弱项强化”。

学生无需自己查找内部能力节点。

### 决策 6：三层架构不变

- 第一层：纯计算；
- 第二层：资料分析专用计算方法；
- 第三层：资料分析实战决策。

用户已有的带“选项判断”的放缩法设计属于第三层参考。当前可以借鉴其“一个方法一个完整界面”的交互思想，但不能提前把真实资料分析选项判断、方法决策等内容塞入第一层。

## 后果

### 正向影响

- 手机端选择成本显著降低；
- 学生不用学习内部能力树；
- 160 个微能力的诊断价值仍完整保留；
- 方法训练能更接近真实思考过程；
- 后续第二层/第三层可以沿用同一产品原则；
- 自动推荐真正从“推荐一个节点”升级为“推荐一个可直接练的任务”。

### 代价与风险

- 需要新增“学生训练项目 → 多个微能力”的映射层；
- 当前 160 个直接 `skill_drill` 入口将不再等同于正式产品菜单；
- 某些现有专项生成器未来可能只作为后台抽题器，不再独立暴露；
- 弱项强化需要设计结构权重，而不能简单选择一个 `skillId` 就结束；
- 前台项目数必须持续克制，不能把能力树换一批名字重新铺出来。

---

## 兼容策略

实施时：

- 不删除 `SkillRegistry`；
- 不重写旧历史；
- 旧 `skill_drill` 数据继续可读；
- 现有 Mastery / Diagnostic 仍按微能力统计；
- 如新增 `trainingProjectId`，与 `skillId` 并存；
- 160 单能力入口可先隐藏为开发/诊断入口，是否彻底删除后续另决策。

---

## 当前不实施的内容

本 ADR 只冻结产品方向，**本次不修改业务代码，不重做现网 UI，不部署**。

正式开发前还需要单独确认：

1. 第一层最终学生可见项目清单；
2. 每个项目对应的交互类型；
3. 今日训练 / 弱项强化在数据不足时的降级策略。

确认后再进入代码重构。
